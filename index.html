Your automation says it succeeded. It didn’t.

A structured reliability review of one exported n8n workflow — aimed at the failure that never raises an error, never marks a run red, and surfaces weeks later as a customer who says they sent something you never got.

The failure this is about

“Our automations run. But every so often a customer says they sent something and we never got it, and we can’t tell whether that’s true, how often it happens, or which ones it happened to.”

The reason that is hard to chase is that nothing went wrong in a way n8n can see. A node returned a clean 200. A payload shape changed upstream and a mapping quietly produced nothing. A duplicate check passed twice because two executions overlapped. The execution list shows green runs, so there is no error to search for and no failed run to open.

Every one of those is visible in the workflow’s own export, before anything runs. That is what this review reads.

What the review is

A structured reliability review of one exported n8n workflow: static analysis of the export, plus manual judgement, plus whatever execution evidence you choose to share.

The analysis is deterministic and it derives, from the export alone: the node inventory and connection graph, triggers, Code-node structure, nodes that can fail with nowhere to send the failure, paths that end without recording anything, the non-atomic static-data idempotency pattern, isolated nodes, unwired Merge inputs, webhook triggers with no authentication configured, credential references, secret-shaped parameter keys, and unrecognised node types.

Three properties that are the actual product

  • Nothing from your export is ever executed. No node runs, no request is made, and no credential value is read. Code nodes are inspected as text.
  • No parameter value and no Code-node body is printed in the report — a blanket rule rather than a filter, because a filter is a list of the leaks somebody thought of.
  • Every finding carries what it does not prove. “This workflow contains an unhandled failure path” and “this workflow has failed” are different claims, and an export can only support the first.

The deliverable is a report you can verify without trusting the person who wrote it. That is the product. The tooling underneath it is not the point.

What it is not, and cannot become

Stated here rather than discovered later, because a review that overstates its reach is worse than no review — it spends your engineers’ time on work that was never needed.

  • It is not “we reproduce your workflow end to end”. Your workflow is never run. There is no n8n execution engine here and none is planned.
  • No n8n expression is evaluated. A wrong expression is invisible to static analysis.
  • No Code node is executed. Code-node findings are lexical — the source is read as text.
  • Nothing is said about your credentials. Only the reference is read, so nothing here establishes whether a credential is valid, expired, or over-scoped.
  • Instance configuration is not in an export. A global error workflow, execution timeouts, queue mode, concurrency settings and your n8n version can all change the conclusions.
  • Runtime history is not in an export. Nothing derived from a file says how often a path has actually been taken.
  • Where a finding cannot be reproduced, it is reported as observed by inspection, not reproduced — and labelled that way. A finding you cannot reproduce is withdrawn, not defended.
